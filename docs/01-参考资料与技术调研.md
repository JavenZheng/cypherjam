## 1. Strudel 是什么

### 1.1 定位与来源

**已确认：Strudel 是 Tidal Cycles 的 JavaScript 移植，定位是浏览器里的 live coding（现场编程）音乐平台。**

- 官网原话：Strudel 是 “a JavaScript version of tidalcycles”，而 TidalCycles 是用 Haskell 写的 live coding 音乐语言。
- Workshop 文档原话：Strudel 是 “an official port of the Tidal Cycles pattern language to JavaScript”。
- 原 GitHub 仓库 `tidalcycles/strudel` 已于 2025-06-19 归档，README 指向 `codeberg.org/uzu/strudel`；官网当前也把源码与许可证链接到 Codeberg。
- 许可证：**AGPL-3.0-or-later**（官网与 npm 均标注）。这意味着如果修改后以网络服务形式提供，通常需要提供对应源码；具体商用边界需法务确认（**推断 / 需法务**）。

### 1.2 技术架构：pattern 引擎 + superdough 音频引擎

**已确认：Strudel 的核心是“Pattern 查询 + 事件调度 + Web Audio 输出”，默认音频引擎是 superdough。**

技术手册描述的 REPL 控制流：

1. 用户代码经转译（transpile）与求值（evaluate），得到 `Pattern` 实例。
2. `Scheduler` 按固定间隔查询当前 `Pattern`，生成下一时间段的 `Events`（也叫 `Haps`）。
3. 每个事件调用 `onSchedule`，交给输出层发声。

关键细节（**已确认**，来自技术手册）：

- 当前查询间隔是 **50ms**，`minLatency` 是 **100ms**，因此“改代码到听到变化”的延迟约为 **50–150ms**。
- `Pattern.queryArc(time, time + interval)` 是**纯函数**：给定时间区间返回事件集合，不依赖外部状态；理论上可以用任意查询间隔，也可以用外部调度器驱动它（**推断**，需验证）。
- 默认输出是 Web Audio；技术手册把 superdough 称为 Strudel 的默认音频输出，并给出 `registerSound(name, onTrigger, data)` 的注册方式；`onTrigger(time, value, onended)` 的 `time` 是 AudioContext 时间。
- 除 Web Audio 外，Strudel 还支持 MIDI、OSC、MQTT 输出；也可以接 SuperDirt（需要额外安装软件）。

### 1.3 运行在浏览器还是需要服务端

**已确认：播放本身在浏览器完成，不需要自建服务端。**

- REPL 是浏览器内的 live coding 环境；superdough 基于 Web Audio API。
- `@strudel/web` 的 README 示例是“保存成 HTML，双击打开”，只需一次点击即可播放；这说明最小运行形态是纯前端。
- **但采样文件仍需通过网络加载**：`@strudel/web` 默认不加载外部采样，需要 `samples('github:tidalcycles/dirt-samples')` 或自己的采样地址；生产环境通常要自己托管 / CDN 化音色包（**推断**）。
- 因此更准确的说法是：**计算与发声不需要服务端；音色资源分发仍需要网络与静态托管**。

### 1.4 `@strudel/*` npm 包是否可以单独引入

**已确认：可以。Strudel 被拆成多个独立 npm 包，`@strudel/web` 是面向网页的一体化入口，`superdough` 也可以单独使用。**

npm registry 查询到的包（2026-11-07）：

- `@strudel/core`：pattern 核心
- `@strudel/mini`：mini-notation 解析
- `@strudel/tonal`：音高 / 和弦等 tonal 功能
- `@strudel/webaudio`：Web Audio 输出辅助
- `@strudel/web`：把多个包打包成易用的网页入口，当前版本 **1.3.0**
- `superdough`：Web Audio 合成器 / 采样器，当前版本 **1.3.0**；npm 描述为 “simple web audio synth and sampler intended for live coding”，技术手册称其为 Strudel 默认音频输出

`@strudel/web` 的最小用法（README 示例，README 标注版本 1.0.3，当前包已是 1.3.0）：

```js
initStrudel();
note("<c a f e>(3,8)").jux(rev).play();
hush();
```

也支持 `evaluate('note("c a f e").jux(rev)')` 把用户输入当 Strudel 代码执行。

**注意：**

- **“能单独引入”不等于“适合直接做产品底座”**：包是 AGPL，且 API、文档、默认音色仍在演进；Getting Started 明确写着项目仍是 experimental / work in progress。
- `@strudel/web` 默认不加载外部采样；REPL 自带的默认鼓组 / 音色是另一套加载方式，生产环境要自己确认音色包许可证与托管方式（**待核实**）。

### 1.5 与“多人实时”的关系

**已确认：官方 REPL 本身不是多人实时房间；多人协作主要靠外部项目 flok。**

- Strudel 官方博客提到，协作式 live coding 编辑器 **flok** 早期就支持 Strudel，后来还支持多个 Strudel 实例；作者用 flok 做过跨地域 jam。
- flok 的 README 自述是 “Web-based P2P collaborative editor for live coding music and graphics”，支持 Strudel；许可证 GPL-3.0，开发已迁到 Codeberg。
- 因此：**Strudel 提供 pattern 语言与声音引擎，flok 提供多人编辑 / 会话层；二者不是同一个东西。**

## 2. Tone.js 的能力边界

### 2.1 定位与版本

**已确认：Tone.js 是 Web Audio 的框架层，不是完整的 DAW，也不是 pattern 语言。**

- 官网定义：“Tone.js is a Web Audio framework for creating interactive music in the browser.”
- 提供 DAW 常见能力：global transport、prebuilt synths、effects；同时提供底层 building blocks，便于自己搭合成器、效果器和控制信号。
- npm 当前版本 **15.1.22**，许可证 **MIT**（2026-11-07 查询 npm registry）。

### 2.2 Transport 定时精度

**已确认：Transport 的调度目标是 AudioContext 时间，属于“采样级调度”；但回调函数本身不是采样级执行，回调参数里的 `time` 才是精确时间。**

- `Tone.Clock` 文档原话：它是 “a sample-accurate clock”；“the callback is not sample-accurate (it is susceptible to loose JavaScript timing), but the time passed to the callback is precise.”
- Transport 关键 API：
  - `Tone.Transport.schedule(callback, time)`
  - `Tone.Transport.scheduleRepeat(callback, interval, startTime?, duration?)`
  - `Tone.Transport.scheduleOnce(callback, time)`
  - `Tone.Transport.start(time?)` / `stop()` / `pause()`
  - `Tone.Transport.bpm`、`seconds`、`ticks`、`PPQ`
- 默认值（源码默认值，**已确认**）：
  - BPM 120
  - PPQ **192**
  - swing 0
- 调度提前量（**已确认**，来自 `Context.ts` 与 Tone.js Performance 文档）：
  - `Context.lookAhead` 默认 **0.1 秒**
  - `Context.updateInterval` 默认 **0.05 秒**（源码中 lookAhead 会参与 updateInterval 计算）
  - `latencyHint` 默认 `"interactive"`（优先低延迟）
  - `Tone.now()` = AudioContext 当前时间 + lookAhead；`Tone.immediate()` 不带 lookAhead
- 官方建议：`Tone.getTransport().start("+0.1")`，提前 100ms 启动，避免调度错误。
- Transport 回调由 **Web Worker 定时器**驱动，不与动画帧同步；官方明确要求**不要在 Transport 回调里直接做 DOM / 绘制**，要用 `Tone.Draw` 把视觉同步到音频时间。

**边界：** 采样级调度只解决“相对 AudioContext 的时间精度”，不解决设备输出延迟、跨设备时钟差异、网络抖动；这些要自己做（见第 4 节）。

### 2.3 内置合成器与效果器

**已确认（来自 `Tone/instrument/index.ts` 与 `Tone/effect/index.ts` 的导出列表）：**

- 乐器 / 合成器：
  - `Synth`、`MonoSynth`、`PolySynth`
  - `FMSynth`、`AMSynth`、`DuoSynth`
  - `PluckSynth`、`NoiseSynth`
  - `MembraneSynth`、`MetalSynth`
  - `Sampler`
- 效果器：
  - `AutoFilter`、`AutoPanner`、`AutoWah`
  - `BitCrusher`、`Chebyshev`
  - `Chorus`、`Distortion`、`FeedbackDelay`、`PingPongDelay`
  - `Freeverb`、`JCReverb`、`Reverb`
  - `FrequencyShifter`、`PitchShift`
  - `Phaser`、`Tremolo`、`Vibrato`
  - `StereoWidener`、`ReverseDelay`
- 另外还有 `Filter`、`Compressor`、`Limiter`、`EQ3` 等组件（未逐一枚举）。

### 2.4 采样加载

**已确认：Tone.js 提供采样播放与加载能力，但不附带完整的商用音色库；资源 URL 需要自己提供。**

- `Tone.Player`：单个采样
- `Tone.Players`：多个命名采样
- `Tone.Sampler`：按音符映射的采样乐器
- `Tone.GrainPlayer`：颗粒化播放
- `Tone.ToneAudioBuffer` / `Tone.ToneBufferSource`：缓冲区与源节点
- `Tone.loaded()`：等待所有 `ToneAudioBuffer` 加载完成

官方示例使用 `tonejs.github.io/audio/...` 这样的示例音频地址；这只是示例资源，不等于可直接商用的音色库（**推断**）。

### 2.5 “序列化”要澄清：`schedule` 是调度，不是保存工程

**已确认：`Tone.Transport.schedule` 是事件调度 API，不是序列化 API。**

- 它做的是“在某个 AudioContext 时间点调用回调”，不会把合成器、效果器、连线、采样、工程状态保存成文件。
- 对 `Transport.ts` 的源码检索没有发现 `toJSON` / `fromJSON` / `serialize` 这类工程序列化入口；Transport 暴露的是 `state`、`bpm`、`position`、`ticks` 等运行状态。
- **推断：Tone.js 核心没有“工程级序列化格式”；要保存作品，需要自己定义事件 / 轨道模型并持久化，或者只用它做运行时引擎。**
- MIDI 文件的读写属于独立包 `@tonejs/midi`，不在 `tone` 核心内（**已确认**，npm 包存在）。

### 2.6 移动端 AudioContext 解锁

**已确认：iOS 上 Web Audio 必须由用户手势触发；Tone.js 提供 `Tone.start()` 来启动 / 恢复 AudioContext。**

- Apple 官方文档明确：在 iOS 上，Web Audio API 要求声音由明确的用户动作触发，例如 tap；在 `onload` 里调用 `noteOn()` 不会发声。
- Tone.js 的 `start()` 返回 Promise；应在 `click` / `keydown` / `pointerup` 等用户手势中 `await Tone.start()`，再创建或播放音频。
- iOS Safari 在用户离开页面（切 tab、最小化、关屏）时会把 AudioContext 置为 `interrupted`，需要重新 `resume()`；MDN 给了 `audioCtx.state === "interrupted"` 的处理示例。

### 2.7 能力边界小结

**Tone.js 不提供：**

- 现成的 pattern / mini-notation 语言（要自己写事件模型）
- 完整的音色库（要自己准备采样并处理授权）
- 跨设备 / 多人的网络同步
- 工程文件序列化格式
- 现成的 UI、DAW 界面、协作房间
- 服务端能力

**Tone.js 提供：** Web Audio 之上的调度、合成、效果、采样、分析、离线渲染等积木。它适合做“时钟 + 声音运行时”，不适合单独当“产品”。

## 3. 两者关系：能不能都用，谁做节拍基准

### 3.1 定位差异

| 维度 | Tone.js | Strudel |
| --- | --- | --- |
| 层次 | Web Audio 框架 / 运行时 | pattern 语言 + 音频引擎 |
| 输入方式 | JavaScript API | mini-notation、JavaScript |
| 音色 | 合成器 + 效果器 + 自备采样 | 自带音色 / 鼓组体系 + superdough |
| 调度 | Transport，采样级调度，lookAhead 可调 | Scheduler，50ms 查询间隔，50–150ms 延迟 |
| 工程保存 | 无内建工程序列化 | pattern 代码本身可保存 / 分享 |
| 多人 | 无 | 官方 REPL 无；flok 外部支持 |
| 许可证 | MIT | AGPL-3.0-or-later |

### 3.2 能不能都用

**技术上可以，但不能让两套时钟各自为政。**

- 两者都建立在 Web Audio 之上；Tone.js 可以操作 AudioContext，Strudel 的 superdough 也使用 Web Audio。
- **推断：** 同时使用意味着两个调度器、两个事件模型、两套延迟参数；如果不统一，会出现“同一拍两次发声 / 时间漂移 / 延迟叠加”。
- 可行的组合方式（**推断，需验证**）：
  1. 用 Tone.js Transport（或自写 Web Audio 调度器）做唯一时钟；
  2. 只把 Strudel 的 `Pattern.queryArc` 当纯函数，查询出事件后交给 Tone.js / Web Audio 调度；
  3. 或者只用 Strudel 的 superdough 发声，但不要同时启动 Strudel 自带 Scheduler。
- **待核实：** Strudel 的 `Scheduler` 是否能接入外部统一时钟；两者能否共享同一个 `AudioContext` 而不产生冲突。验证方式：读 `@strudel/core` 的 scheduler 源码，写一个最小实验，记录事件时间与 Tone.js Transport 的偏差。

### 3.3 多人实时房间：谁更适合做节拍与同步基准

**结论：如果要做“多人实时同步的浏览器音乐房间”，Tone.js 更适合做节拍 / 时钟基准；Strudel 更适合做 pattern 语言与声音层，不适合直接当网络时钟。**

理由（**已确认事实 + 推断**）：

1. **Tone.js 的 Transport 直接以 AudioContext 时间调度**，可以在未来某个精确时间 `start(time)`，也支持 `scheduleRepeat` 把事件排到未来；这正好适合“服务器给出下一小节的时间戳 → 客户端换算成本地 AudioContext 时间 → 提前调度”。
2. **Strudel 的 Scheduler 是为 live coding 设计的**：50ms 查询间隔、100ms `minLatency`、50–150ms 延迟；它追求“改代码后很快听到变化”，不是“多设备同一拍对齐”。
3. Strudel 的 `Pattern.queryArc` 是纯函数，**理论上可以**由外部时钟驱动；但这需要自己写适配层，且不在官方承诺范围内（**推断 / 待核实**）。
4. 如果只追求“同一拍对齐”，直接用 Web Audio + 自写调度器也可以；Tone.js 是便利层，不是唯一选择（**推断**）。
5. 如果产品核心是“loop / pattern 的即时编辑”，Strudel 的表达力更强；但同步基准仍应独立出来，不要让 pattern 调度器兼任网络时钟（**推断**）。

## 4. 多人同步的真实难点

### 4.1 为什么 Web Audio 做不到“网络级精确同步”

**已确认 / 机制层面：**

- 每台设备的 `AudioContext.currentTime` 是**本地时钟**，起点不同；不能直接把 A 设备的 `currentTime` 发给 B 设备使用。
- 即使把同一个“未来时间”换算到各自 AudioContext，**实际发声还会叠加设备输出延迟**；`outputLatency` 因设备、浏览器、耳机而异。
- 设备晶振存在偏差：**推断计算**，50ppm 的偏差约为 0.05ms/秒，即 **3ms/分钟、30ms/10 分钟**；一次性对齐会慢慢漂走，需要周期性重同步。
- 网络抖动、Wi-Fi 拥塞、不同设备性能，会让“收到消息的时间”不等于“应该发声的时间”。

### 4.2 常见做法与代价

| 做法 | 基本机制 | 代价 / 风险 | 适用 |
| --- | --- | --- | --- |
| 服务端统一时钟 | 服务器维护唯一的 beat timeline；客户端通过 NTP 式四时间戳估算 offset / RTT，把服务器 beat 映射到本地 AudioContext 时间 | 需要服务端 + WebSocket + 时钟同步算法 + 抖动缓冲；精度受 RTT/2 与网络抖动限制 | 多人房间、跨网络 |
| 客户端偏移补偿 | 客户端测得到参考时钟的 offset，在本地调度时补偿；持续估计漂移 | 客户端逻辑复杂；需要可靠参考源；漂移校正策略要做 | 无强服务端、或服务端只做广播 |
| 以主机时间戳为基准 | 房间内一台“主机”定义节拍，其他人跟随主机时间戳 | 主机依赖强；主机延迟 / 掉线会影响全员；适合小房间 | 小型、同房间、低复杂度 |
| Ableton Link / 原生桥 | Link 在局域网同步 beat / tempo / phase / start-stop；官方是 C++ SDK / iOS LinkKit | 浏览器没有官方 Link API；需要原生桥或 WASM 封装；不是纯 Web | 局域网、原生生态 |
| WebRTC 音频流 | 服务器 / 一端混音后推流 | 端到端延迟通常远高于本地合成；不适合紧合奏；带宽 / 服务成本高 | 语音、广播、非紧合奏 |

**已确认案例：**

- WAC 2016 论文《Synchronisation for Distributed Audio Rendering over Heterogeneous Devices, in HTML5》报告：使用共享参考时间，在测量设备上做到 **1–10ms 单设备精度、5ms 标准差**，低于音频块时长。
- Beatsync 是开源的“多设备同步播放器”：用 **NTP 启发式**的 WebSocket 时钟同步，目标是毫秒级；README 明确说移动端支持仍是 experimental。
- Ableton Link 官方文档：同步 beat、tempo、phase、start/stop，跨应用 / 设备，基于本地网络；核心是 C++ 库，iOS 用 LinkKit；**没有浏览器原生 API**。

### 4.3 “听起来齐”需要什么精度

**结论：没有单一数字，取决于场景；但可以用以下区间做工程目标。**

- **≤10ms**：很紧，接近“同一台设备”的听感；适合对节拍敏感的电子乐 / house。
- **10–30ms**：多数人可接受，可能有轻微“双音 / flam”，但派对环境常被环境声掩盖。
- **30–40ms**：开始明显；复杂音乐中可能被感知为“不齐”。
- **>50ms**：明显延迟，不适合紧合奏。

依据：

- Haas 经典研究：两个事件被听成“同时”的阈值大约 **25–30ms**（转引自 telematic performance 论文）。
- 歌唱合奏研究：复杂声音（语音 / 音乐）的异步感知阈值常被引用为 **40ms**。
- 一项音频延迟 JND 研究：在 0ms 基础延迟下，平均 JND 约 **49ms**；有音乐训练的人更敏感。
- WAC 论文的 1–10ms 是**系统测量精度**，不等于人耳阈值；两者不要混用。

**同房间 vs 跨网络：**

- 同一房间、所有人听**同一个音箱 / PA**：只需要同步“控制与画面”，不需要多设备音频对齐；难度低很多（**推断**）。
- 同一房间、每台手机各自外放：要同时处理每台设备的输出延迟（iOS 常见数十毫秒），必须逐设备校准；否则鼓点会叠成“双拍”。
- 跨网络房间：RTT 通常 20–100ms，offset 估计误差约 RTT/2；即使算法很好，也难稳定做到 <10ms。实践上要“提前 1–2 小节调度 + 抖动缓冲”，目标 20–40ms 更现实（**推断**）。

### 4.4 工程检查清单

- 用 **AudioContext 时间**做调度，不要用 `Date.now()` / `performance.now()` 直接排音频。
- 服务器给出“下一小节开始”的 beat 时间戳；客户端换算为本地 AudioContext 时间，并**提前调度**。
- 补偿 `outputLatency`；iOS 18.4 起支持 `AudioContext.outputLatency`，更早版本需要实测校准（**已确认 API 支持版本**）。
- 周期性重同步，处理时钟漂移；不要只对齐一次。
- 关键场景避免蓝牙耳机；蓝牙会额外引入百毫秒级延迟。
- 处理 iOS 的 `interrupted` / 锁屏 / 来电，恢复后重新对齐，而不是继续用旧时间轴。
- UI 动画不要跟音频调度回调硬绑；用 `Tone.Draw` 或自己的视觉时钟。

### 5.3 观察

- **零基础产品大多是单机**：Incredibox、Chrome Music Lab、Patatap、House Cube、Drumbit 都是单人操作；多人最多是“分享作品 / 投票”，不是实时合奏。
- **实时多人产品大多是 DAW / loop studio 或休闲 swipe**：Audiotool、Soundation、Endlesss 偏制作 / loop；WEJAM、JamGroovin 偏休闲实时。**“派对现场多人合奏”确实有先例，但多为小众 / 新项目，且没有找到经独立验证的大规模案例。**
- **house 场景的零基础交互已经有人做**：House Cube 用“立方体开关 loop”把 four-on-the-floor 拆成可点选的层；Drumbit 用 16 步网格。它们都不是多人。
- **live coding 路线存在但偏小众**：Strudel / TidalCycles 在 algorave / 电子乐现场有真实使用；flok 证明“浏览器 + 多人 + live coding”可行，但受众是愿意写代码的人。
- **事实层面，未找到一个同时满足“house + 零基础 + 手机 + 同房间实时合奏”的大规模产品**；这不等于没有需求，只说明没有可验证的成熟先例（**推断**）。
- **音乐类型的技术含义（推断）**：house 的 four-on-the-floor 每拍都有 kick，相位错误会比稀疏节奏更明显；loop / 16 步网格天然适合量化，但也更容易听出“双拍”。这会让同步精度成为体验的关键变量，而不是可忽略的细节。

## 6. 手机端风险清单（以 iOS Safari 为主）

| # | 风险 | 依据 | 影响 | 验证方式 |
| --- | --- | --- | --- | --- |
| 1 | **首次发声必须用户手势** | Apple 官方文档：iOS 上 Web Audio 必须由 tap 等明确用户动作触发；`onload` 里播放不会响 | 自动播放失败、页面“看起来没声音” | iPhone Safari 打开测试页，分别测试“自动播放”和“点击后播放” |
| 2 | **静音开关 / audio session** | WebKit Bug 237322：Web Audio 默认走 ambient / ringer 通道，手机侧边静音开关会静音；iOS 17 起可设 `navigator.audioSession.type = "playback"`；MDN 标注该 API Safari 16.4+ 支持 | 用户以为坏了；派对现场被静音开关坑 | 真机拨到静音，测试默认 / `playback` 两种设置；记录 `navigator.audioSession.type` |
| 3 | **锁屏 / 切后台 / 关屏中断** | MDN：iOS Safari 在切 tab、最小化、关屏时 AudioContext 变为 `interrupted`，需要 resume；Apple 开发者论坛称 Web Audio / WebRTC 在锁屏或后台会被 suspend | 音乐停止、时间轴失效；无法真正后台播放 | 真机播放中锁屏 10 秒 / 切到其他 App / 切 tab，恢复后记录 state 与是否继续 |
| 4 | **来电 / 其他音频抢占** | MDN：`interrupted` 可由电话 / 会议 App 等外部中断触发；Apple 原生 AudioSession 文档描述来电会 suspend | 中断后需要重新同步，不能假设时钟连续 | 播放中来一通电话 / 触发 Siri / 播其他音乐，恢复后检查 offset |
| 5 | **输出延迟** | MDN：`AudioContext.outputLatency` 在 Safari / iOS 18.4 起支持；第三方汇总称 iOS Safari 往返延迟约 30–60ms | 多设备对齐需要逐设备补偿；节拍听起来偏晚 | 真机记录 `baseLatency` / `outputLatency`；用麦克风回环测实际延迟 |

| 7 | **内存 / 解码崩溃** | Tone.js Performance 文档：在手机等内存受限设备上，加载很多 / 很大的音频文件，解码时可能把浏览器搞崩 | 采样包过大导致首次加载失败 / 闪退 | 低端 iPhone 上加载目标音色包，记录崩溃与加载时间 |
| 8 | **发热 / 降频** | **推断**：连续合成 + 大量节点 + 图形渲染会持续占 CPU / GPU；未找到官方量化数据 | 长时间播放掉帧、音频 glitch、手机烫 | 真机连续播放 10–15 分钟，记录 `currentTime` 漂移、掉帧、温度 / 电量变化 |
| 9 | **屏幕自动熄灭 / 无 Wake Lock** | **待核实**：未确认目标 iOS 版本对 Screen Wake Lock 的支持与限制 | 演奏中熄屏，触发中断 | 真机设置最短自动锁屏，观察是否熄屏；查 Safari 版本对 Wake Lock 的支持 |
| 10 | **PWA / 后台播放限制** | Apple 论坛：iOS Safari 中 Web Audio / WebRTC 在锁屏或后台被 suspend；Web 应用无法像原生音乐 App 那样常驻后台 | 不能做“锁屏继续 jam”；用户切走就断 | 用“添加到主屏幕”的 PWA 再测锁屏 / 切后台 |

**观察：**

- 真正“开箱即用”的浏览器多人实时音乐同步项目很少；**Beatsync 最接近“时钟同步 + Web Audio 播放”的参考实现**，但它是播放器，不是协作创作工具。
- **flok / Estuary 更接近“多人协作创作”**，但它们是 live coding 场景，用户需要写代码；同步层依赖 P2P 或服务器会话，精度没有公开量化（**待核实**）。
- **Ableton Link 是节拍同步的成熟方案，但不是 Web 方案**；要在浏览器用，需要原生桥 / WASM 封装，成本和维护风险都高（**推断**）。
- **Tone.js 不自带多人同步**；可行路线是自己实现“服务器统一 beat timeline + NTP 式 offset + 客户端 AudioContext 调度 + outputLatency 校准”（**推断**，可参考 Beatsync 的时钟做法）。

## 9. 关键结论与待核实清单

### 9.1 关键结论

1. **Strudel 是 Tidal Cycles 的官方 JS 移植，浏览器内运行，默认音频引擎是 superdough；`@strudel/*` 与 `superdough` 都可单独 npm 引入。** 它的 Scheduler 当前是 50ms 查询间隔 + 100ms `minLatency`，改代码到听到变化约 50–150ms；这适合 live coding，不适合直接当多人网络时钟。许可证是 AGPL-3.0，商用前需法务确认。
2. **Tone.js 是 MIT 的 Web Audio 框架，Transport 能做到采样级调度，合成器 / 效果器 / 采样能力完整；但它没有内建网络同步、工程序列化、多人房间或音色库。** 默认 `lookAhead` 0.1s、`updateInterval` 0.05s，回调由 Web Worker 驱动；iOS 必须用户手势启动，锁屏会 `interrupted`。
3. **如果做多人实时音乐房间，Tone.js（或自写 Web Audio 调度器）更适合做节拍 / 同步基准；Strudel 更适合做 pattern / 声音层。** 两者可以组合，但必须统一为一个时钟，不能让两个 Scheduler 各自跑；Strudel 的 `queryArc` 是纯函数，可被外部调度器驱动的可行性仍需验证。
4. **“听起来齐”不是单一精度指标：≤10ms 很紧，10–30ms 多数可接受，30–40ms 开始明显，>50ms 不适合紧合奏。** 同房间单 PA 最简单；多台手机各自外放要逐设备校准输出延迟；跨网络房间受 RTT/2 与抖动限制，目标 20–40ms 更现实。WAC 论文的 1–10ms 是系统测量精度，不是人耳阈值。
5. **iOS Safari 是最大风险源：手势解锁、静音开关 / audio session、锁屏中断、输出延迟（第三方汇总 30–60ms）、蓝牙 150ms+、内存解码崩溃，都会单独破坏体验。** 必须真机验证，不能只靠桌面 Chrome。
6. **电子乐 / house 的零基础先例已经存在（House Cube 的 loop 立方体、Drumbit 的 16 步网格、Soundation / Audiotool 的 DAW 与实时协作），但“house + 零基础 + 手机 + 同房间实时合奏”没有找到大规模成熟产品。** 实时多人更常见于 DAW / loop studio 或休闲 swipe（WEJAM、JamGroovin、Endlesss）。
7. **`cypherjam.com` / `.io` / `.app` 在 2026-11-07 均未注册；未发现同名 App / 项目 / 厂牌，但“cypher jam”是街舞圈常见活动名。** 域名可用性不等于商标可用性，商标检索未做。

## 10. 调研局限

- **没有真机测试**：所有 iOS 延迟、发热、锁屏恢复、蓝牙延迟均为文档或第三方数据，不是本项目实测。
- **没有做代码级验证**：Strudel / Tone.js 的“能否共用时钟”“queryArc 外部驱动”属于推断，需要最小实验。
- **Codeberg 仓库页面被反爬拦截**：Strudel 源码细节主要来自官网技术手册、npm registry、GitHub 归档页与公开文档；未逐行读 Codeberg 源码。
- **竞品数据以官网自述为主**：用户量、延迟、活跃度多为厂商宣传，未独立审计。
- **域名与同名只做了 whois / RDAP / 搜索**：没有做商标、社交媒体账号、应用商店全量检索。
